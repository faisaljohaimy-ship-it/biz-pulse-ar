## ٣) الترتيب (كل خطوة بشرط عبور وتراجعٍ مكتوب)

**أ) الآن — بيد المالك، دون كود:**

1. تأكّد أن آخر نشر Vercel من GitHub (✓ مقيس أعلاه) وأن لا التزامات في Lovable خارج `main` (✓ `latest_commit_sha = main`).
2. Lovable ← مشروع «AI Command Center» ← Settings ← GitHub ← **Disconnect**. _التراجع:_ إعادة الربط من الواجهة نفسها.
3. **Unpublish** لموقع `lovable.app` (ما زال علنيًّا). _التراجع:_ Publish من المحرّر.
4. بعدها: دفعة اختبارية صغيرة إلى `main` ثم نشر Vercel — يجب ألّا يظهر أي التزام «Applied …» من Lovable.

**ب) قياسات قبل أي كود (بلا أثر):** 5. جرد أسماء متغيّرات بيئة Vercel (`filter_project_envs` دون فكّ قيم) وتحديد أيّ `LOVABLE_*` موجود فعلًا ← يحسم البنود 5 و6. 6. سجلّ Vercel/Supabase لثلاثين يومًا: هل وصل أيّ طلبٍ إلى `/mcp` و`/lovable/email/*`؟ ← يحسم 3 و5. 7. مطابقة صفوف Lovable Cloud مقابل `cnaevysaoimzusnvpazr` (الفارق 2) — قراءة فقط.

**ج) كود، على فرع، بمعاينة Vercel قبل `main`:** 8. إعداد البناء القياسي (البند 2) — الشرط: `tsc` + الاختبارات كاملةً + `npm run build` + ميزانية الأداء (JS 9.95/10.00 MiB — لا هامش) +
مقارنة ملفّات `.vercel/output` ومعاينة تعمل على `/` و`/api/chat/health`. **التراجع:** `git revert`. 9. الدخول المباشر عبر Supabase (البند 4) — الشرط: Google مفعَّل في Supabase، واختبار دخول فعليّ بحسابٍ تجريبي، ولا مسّ لـ`/auth/v1/token` للجلسات القائمة. 10. البريد (البند 5) — الشرط: بريد اختبار (تسجيل/استعادة) يصل من المسار الجديد **قبل** إزالة القديم. 11. موصّلات `LOVABLE_API_KEY` (البند 6) — واحدًا واحدًا، بمفتاحٍ جديد لكلٍّ، وفحص تكاملٍ حيّ. 12. حذف الحزم والمسارات والمتغيّرات **آخر شيء**، بعد أسبوع مراقبة بلا استعمال (سجلّات) — وحذف Lovable Cloud بإذنٍ صريح مستقل.
