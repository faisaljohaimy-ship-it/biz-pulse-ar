# Case Study Writer

Turn a finished (or in-flight) project into a persuasive, credible case study that shows judgment, not just output.

## When to trigger

- "Write a case study about this project"
- Portfolio pieces, client success stories, award/tender submissions
- Turning a repo, changelog, or project summary into a narrative

## Process

1. **Gather the raw material**: from the conversation, repo, or ask up to 3 targeted questions max (client/context, hardest constraint, best measurable outcome). Never invent metrics.
2. **Structure**:
   - **Context** — who, what product, what stakes (2–3 sentences)
   - **Problem** — the real constraint, stated concretely
   - **Approach** — key decisions and trade-offs (this is where expertise shows)
   - **Solution** — what was built, in plain language, one technical highlight max
   - **Results** — numbers first; if none exist, state qualitative outcomes honestly
   - **Lessons** — one honest reflection (optional but powerful)
3. **Voice**: confident, specific, zero buzzwords. Short sentences. Claims tied to evidence.
4. **Length**: 400–700 words default; offer a 100-word summary variant for LinkedIn/landing pages.

## Rules

- Real numbers only — if the user has no metrics, mark placeholders clearly as `[METRIC]`, never fabricate.
- Name the trade-off: what was deliberately not done and why. Reviewers trust case studies that show judgment.
- Client confidentiality: anonymize on request ("a national utility provider").

## Quality bar

A skeptical technical buyer finishes it thinking "these people make good decisions under constraints" — not "nice marketing."
